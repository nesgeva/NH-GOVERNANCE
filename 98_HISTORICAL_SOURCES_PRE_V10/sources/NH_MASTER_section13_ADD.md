## 13. THE LIVE LOOP — HOW N.H RUNS WITHOUT EVER STALLING  [DESIGNED — not built; concept only, nothing on disk]

*Worked out conversationally in session 8 and demonstrated with throwaway browser widgets that are CONCEPT DEMOS ONLY — not the N.H server, not Python, not on disk. This section records the design so it isn't lost. It does NOT change the forced build order (§7C / §11 item 2); it is how the engine eventually RUNS live, not the engine itself.*

**THE PROBLEM IT SOLVES.** The chat — and far more so, voice — must never freeze. Not on a big message, not while reasoning, not during a multi-second deep search. A text chat can survive a pause; a spoken conversation can't — dead air mid-sentence is broken. So the question is: how does N.H do heavy work (memory, filter, reasoning, web search) while the conversation stays continuously live? §13 is the answer.

**THE SHAPE — A FIGURE-EIGHT, TWO PARTS, CACHE OUTSIDE.** Not a metaphor — the actual reason it doesn't choke. The cache sits OUTSIDE the loop. The loop is two parts. Information flows both directions at once, and nothing ever holds still at the center.

**THE CACHE (outside the loop).** A holding file. The chat writes into it whatever is said; it just fills. It is the buffer that decouples chat-speed from loop-speed, so the chat never waits on the loop and the loop never waits on the chat. (Earlier wrong picture, recorded so it's never re-fought: a "lever" you pull to drop the cache into the loop — WRONG. Nothing is pulled; see fire-and-let-go below.)

**PART 1 — THE STARTER: FIRE-AND-LET-GO.** This is the keystone of the whole loop. Part 1 picks up what's in the cache and IMMEDIATELY hands it off to the deep side — then turns around free in the same instant. It never carries a job through. It never holds. It never waits. It only launches.

**PART 2 — THE DEEP SIDE.** Memory, the filter, the reasoning — AND deep search. Each job runs here on its own clock, in parallel with every other job. When a job is done it does NOT get picked back up — it **announces itself** back toward the chat/cache. Nobody fetches it; it returns on its own when ready.

**WHY THERE IS NO "WORKER COUNT" (the dead end we passed through and discarded).** The instinct is to imagine a swarm of workers and ask "how many?" — but a *number of workers is a ceiling*, and a ceiling contradicts the whole never-stall premise. The real principle is NOT "have enough hands." It is **"no hand ever holds still."** A worker only gets "used up" if it grabs a job and then stands there babysitting it while the slow part runs. Remove the waiting — fire-and-let-go — and no hand is ever stuck, so the count stops mattering. Even one starter can launch jobs forever, because it never stops to wait on any of them. (Recorded wrong turns, never to be re-fought: the *lever* — wrong; the *line-between-two-dots* "worker spanning both parts" — wrong, a fake connection that's still two things with a string between them; the *fixed worker pool / worker count* — wrong, it smuggles in the exact ceiling the design exists to remove. The right frame is fire-and-let-go: no waiting, no count.)

**TWO CONSEQUENCES (the payoff — stated honestly).**
1. **Deep search never blocks.** Deep search is the slowest thing in the system, and in a normal setup it's the worst freeze. Here it's just another deep-side job: the starter fires it and lets go, it runs on its own, the chat stays fully live, and it announces itself back when done. This is what makes "ask N.H to go look something up mid-voice-call and keep talking to it while it does" actually possible. Heaviness of a job only changes how long THAT job takes — never whether the chat stays alive.
2. **Parallel topics become mechanically possible.** If every topic is a fired-and-forgotten job running on its own, nothing forces them to run one-at-a-time. Several trains of thought can be in flight at once, each returning when ready, interleaved — topic C may answer before topic A because A's search is heavier. This is genuinely different from normal one-turn-one-answer-in-order chat. **HONEST LINE (Rule 12):** the *architecture ALLOWS* parallel topics — that is a real, exciting consequence that fell out of the mechanism, not a bolted-on feature. *Making it GOOD* — which answer surfaces when, keeping threads from bleeding into each other, showing several live trains in one chat — is real design work that is NOT done. Do NOT inflate to "N.H can hold many conversations at once" as a built fact. The hard question (can the architecture even do this?) is yes; the rest is still work.

**HOW IT LOCKS INTO THE REST OF N.H.**
- It IS §3C's "two places — dumb memory + fast calculator" / §7A Rule 7 (the membrane), seen from the RUNTIME side. The deep side computes fast; the append-only memory underneath (§6B) stays dumb and safe. Fire-and-let-go is *why* the calculator can be fast without freezing the chat — and the append-only store is *why* firing work off without babysitting it is safe: the deep side can only ever propose layers, never overwrite, so a fast wrong reading is a rejectable layer, never a corruption.
- The non-freeze is the **precondition for voice** (§4 / §9 mobile modes). Without it, voice has to choose between answering fast and remembering; the loop lets it do both at once. This is the mechanical reason voice is even on the table.
- It does NOT reorder the forced engine build (§7C / §11 item 2: reading-layer schema → detector probe → engine). The loop is how the engine RUNS live, especially for voice — not the engine, and not "next." Designed now; built when liveness/voice is actually on the table.

**THE HONEST EDGES (don't overclaim).** Nothing here is coded; the widgets were concept demos in a browser, not the server. The "worker exhaustion" worry dissolved as a *counting* problem (fire-and-let-go removes the ceiling) — but a real implementation still needs sane resource limits and backpressure under genuinely extreme load; that's ordinary tuning, not a broken architecture. The parallel-topic UX is unsolved. Mechanically the loop is plainly buildable (it's a standard producer/cache/async-worker shape — the no-freeze decoupling is *why* that pattern exists); the hard part is still the engine that runs INSIDE the loop (§7C item 2c), which does not exist.

**TRUEST SINGLE LINE (for §13):** The chat never waits because no hand ever holds still — the starter fires each job and lets go, the deep side runs it and announces itself back, so heaviness (a big message, reasoning, a multi-second deep search) only ever changes how long that one job takes, never whether the conversation stays alive — and that same property is what lets several topics run at once and what makes voice possible at all.
